# Verification-contract recording + accounting evidence lenses

# Detailed design — verification-contract recording + accounting evidence lenses

Refines ARCH-026 (verification-contract recording + accounting evidence lenses,
which refines REQ-037). This DDD specifies the evidence model, the runner
contract, the two accounting lenses, and the fingerprint rendered-body hashing
that keeps recording side-effect-free — drawn from the actual implementation
(`lib/verification.py`, `commands/verify.py`, `commands/project_audit.py`).

## 1. The contract (declaration vs recorded run)

An artifact DECLARES a contract in frontmatter; the runner RECORDS the outcome
into DIFFERENT frontmatter fields. Declaration and result are deliberately
separate namespaces so a recorded run never mutates the contract:

| Kind | Fields | Written by |
|---|---|---|
| Declaration | `verify_command`, `verify_exit_code` (default 0), `verify_evidence` | the author (human/AI) |
| Recorded run | `verify_run_at`, `verify_run_exit_code`, `verify_run_out_hash`, `verify_run_git_ref`, `verify_run_command_hash`, (`verify_run_evidence_hash`, `verify_run_evidence_mtime` with `--evidence-file`) | `specflow verify` only |

`verify_run_command_hash` is `sha256:<12hex>` of the current `verify_command`
string. The divergence lens (§3) compares it against the hash stored at last
run to detect a command that drifted after its recorded run — without storing
the whole command twice.

## 2. Function — the runner (`lib/verification.run_one`)

`run_one` executes `verify_command` via `subprocess.run(shell=True, cwd=root)`
and captures: the real exit code, `out_hash = sha256(stdout+stderr)`, an
ISO-8601 `run_at`, best-effort `git rev-parse HEAD`, and `command_hash`.
`build_updates` projects only the pinned field names into the update dict.

**Keystone invariant — runner failure vs recorded failure.** `run_one` returns
`ok=True` whenever the subprocess COMPLETED, regardless of its exit code. A
non-zero `verify_command` exit is RECORDED (`verify_run_exit_code` = that code)
and `specflow verify` still exits 0. The CLI reserves non-zero exit for RUNNER
failures only: unknown artifact ID, timeout (`subprocess.TimeoutExpired`), or
spawn failure. This is accounting-not-policing applied to verification: the
engine never lies about what happened, and never overrides the human.

`--dry-run` prints each artifact's `verify_command` and executes/writes
nothing — the evidence model is observable without side effects.

## 3. The two accounting lenses (`project_audit._verification_lens`)

Both lenses READ the contract/result fields and surface gaps as WARNINGS.
Neither drives the audit/gate exit code — `"verification"` is registered in
`_ACCOUNTING_CONCERNS`, so its warns are excluded from the exit-2 count.

- **Missing-evidence** — an implemented/verified UT/IT/QT/STORY that declares
  `verify_command` but has no `verify_run_at` (declared, never run).
- **Divergence** — `verify_run_exit_code` != declared `verify_exit_code`
  (ran, but the result diverged from the contract); OR `verify_run_command_hash`
  != hash of the current `verify_command` (the command drifted since the last
  recorded run).

A project with zero `verify_command` anywhere degrades to ONE info line — never
a warn — so the lens is silent for projects that do not adopt contracts.

A companion lens, `_ac_coverage_lens` (`"ac-coverage"`, also accounting), counts
a REQ's acceptance-criteria items vs its linked tests (QT direct; IT via ARCH;
UT via ARCH→DDD) and warns only when a REQ with ACs has ZERO linked tests.

## 4. Fingerprint rendered-body hashing (why recording is side-effect-free)

`compute_fingerprint` hashes the artifact BODY only, not the frontmatter.
Because every `verify_run_*` field is written to frontmatter via
`update_artifact`, recording a run NEVER changes the artifact fingerprint and
NEVER sets `suspect`. This is load-bearing: it means an honest verification
recording cannot be mistaken for a content change that would flag the artifact
as drifted. The contract fields (`verify_command`, etc.) are also frontmatter,
so declaring a contract is likewise fingerprint-neutral — only body edits move
the fingerprint.

## 5. Lifecycle placement

The `/specflow-execute` skill runs `specflow verify <ID>` (or `--all`) as a
deterministic step BEFORE transitioning a test/story artifact to `verified`,
mirroring its existing `specflow artifact-lint` step. The recorded
`verify_run_*` evidence is what makes `verified` traced rather than asserted.
A failing run is still recorded; the human decides whether to fix, relax, or
accept — the engine never blocks.

## Options considered

- **Store full stdout in frontmatter.** Rejected — unbounded growth; the
  `out_hash` + optional `--evidence-file` path (hashed by file bytes + mtime)
  give tamper-evidence without bloating the artifact.
- **Make divergence a structural (escalating) warn.** Rejected — re-introduces
  cry-wolf; a drifted command is review-worthy, not release-blocking.
