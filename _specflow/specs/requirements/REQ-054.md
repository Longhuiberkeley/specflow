## Rationale
Approved and verified are stored flags with no record of what content was approved or which run verified it, and suspect propagation is effectively dormant. Auditors ask which version was approved; today nothing can answer.

## Acceptance Criteria

1. Given an artifact moved to approved, when the update succeeds, then the artifact SHALL carry approved_by, approved_at and approved_fp.
2. Given approved_fp, when it is computed, then it SHALL be a versioned fp2 fingerprint over the type's declared normative fields, leaving the v1 body fingerprint unchanged.
3. Given a link created or reviewed after this feature ships, when it is written, then it MAY carry an fp field holding the target's fingerprint at that time.
4. Given every link writer (update links, add-link, renumber-drafts, role normalisation, ReqIF import and export), when it rewrites a link, then unknown link keys SHALL survive the round trip.
5. Given an artifact whose normative content changed after approval, when lint runs, then an approval_stale finding SHALL be emitted at accounting severity, with 0 findings for unstamped legacy artifacts.
6. Given a stamped link whose target fingerprint differs from its stamp, when lint runs, then a derived suspect finding SHALL be emitted at accounting severity.
7. Given the clear-suspect command, when it runs on a stamped link, then it SHALL re-stamp the link and record who and when as an evidence event.
8. Given a unit, integration or qualification test with status verified whose last recorded verify run's exit code differs from its declared verify_exit_code (default 0), when lint runs, then a verified_contradiction finding SHALL be emitted at accounting severity.
9. Given the dormant semantic path of suspect propagation and the unread auto_flag config key, when this requirement is implemented, then both SHALL be removed with a CHANGELOG entry stating that suspect is now derived.
