# Lint negative-fixture coverage

## Context

artifact-lint guards the repository, but the guard itself is unguarded: existing tests prove checks pass on good input, and none proves a check trips. A check that quietly matches nothing looks identical to a pass forever. Measured at v1.17.3 (grep over tests/): 28 of 48 artifact-lint rule ids appear in zero test files — including blocking checks such as story-linkage/beyond-draft, ids/duplicate, and status/invalid. pstack-claude shipped this exact bug class for a whole release (a check hunting a retired slug); its invariants suite is the countermeasure adopted here. Derived from poteto/pstack and michael-denyer/pstack-claude (MIT).

## Obligation

- OBL-1 (RFC 2119): Every artifact-lint rule id MUST have a test fixture that provably trips it. The rule-id set MUST be enumerated from artifact-lint source (the `_emit(findings, "<rule-id>"` literals), never hand-copied, and coverage MUST fail in both directions — a rule id without a fixture, and a fixture without a rule id.

## Acceptance Criteria

1. Given the shipped artifact-lint source, when the test module enumerates `_emit` rule-id literals, then the enumerated set equals the fixture-registry key set, with missing and stale ids named in the failure message.
2. Given any rule id in the registry, when its builder mutates a scaffolded project tree and lint runs on it, then a finding carrying that exact rule id is present (one parametrized case per rule id).
3. Given a developer adds an artifact-lint rule without a fixture, when the suite runs, then the coverage test fails naming the uncovered rule id.
4. Given a rule id is retired from artifact-lint while its fixture remains, when the suite runs, then the coverage test fails naming the stale fixture.
