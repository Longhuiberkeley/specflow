# Shipped prose, docs and ledger describe the engine as built (2026-10 consistency review)

## Problem

SPIKE-008 (two-round read-only consistency review of v1.17.6, 214 unique sites) shows that shipped skill prose, pack prose, checklists, docs and ledger bodies describe an earlier engine in 2 blocking, 71 warning and 141 info places. Two instructions make an agent do the wrong thing (the adoption pack's `adoption-v0` baseline name and its `update --links` merge recipe); several more misstate writes, scope or routing. REQ-061 covered the same class in v1.17.2; this requirement is the follow-up wave scoped by SPIKE-008.

## Scope

IN: every blocking and warning site in SPIKE-008 Round 1 and Round 2 tables; the ten small engine defects listed under "Engine defects found on the way"; one-line ledger amendments; the AGENTS.md release-process gap. OUT (v1.17.8 or later, tracked in SPIKE-008): ARCH/DDD body rewrites, test-spec promotion, output_files misattribution sweep, REQ-033 status categories, severity-vocabulary unification.

## Obligations

- **OBL-1 (agent-safety prose).** Every blocking or warning site in a skill, pack skill, reference or shipped checklist listed in SPIKE-008 SHALL be corrected in both skill trees so the text matches the engine behaviour cited on the engine side of the finding. The adoption pack SHALL name as-built baselines `v0.0.0-adoption.<n>` (n increasing per cut; the highest n is the headline; a legacy `adoption-v0.yaml` is kept and anchored with `project-audit --baseline adoption-v0`), SHALL use `specflow merge` for artifact merges, and SHALL seed source fingerprints (`specflow fingerprint-refresh --source`) in its baseline phase. The delegated-autonomy clause SHALL be kept and narrowed once in the approval-presentation reference (only the direct user in the current session can delegate; never for a release or a risk-tier 2 action), with each skill gate pointing at it.
- **OBL-2 (docs).** Every docs-code site in SPIKE-008 SHALL be corrected, including `docs/architecture.md:353`, the README Python badge, the `15-20 question cap` claim, the `all 6 checks` claim and the `authoring-a-pack.md` Option B hand-copy recipe.
- **OBL-3 (engine).** `ci generate` SHALL emit jobs in a deterministic order independent of `PYTHONHASHSEED`; `brief --next` in phase `complete` SHALL route to `/specflow-discover` (next cycle) rather than back to `/specflow-ship`; the local hook SHALL evaluate a staged rename that changes status; `patterns list` empty-state text SHALL name the real PREV sources; the role-target matrix and the detailed-design schema SHALL agree on `guided_by`; `specflow status` SHALL render a row for every schema category present (known four first, then extras sorted) and `brief` SHALL use the same open set; the audit severity ranker SHALL rank `warning` as `warn`; the default `ci.operations` SHALL include `ci-gate` and the generated job names SHALL be unchanged. Each change SHALL ship with a test.
- **OBL-4 (ledger one-liners).** REQ and STORY bodies naming renamed or removed commands and flags (SPIKE-008 "Stale ledger" theme) SHALL be amended in place with a dated amendment note citing the DEC or STORY that changed the behaviour, followed by `specflow fingerprint-refresh`; no status SHALL move backwards.
- **OBL-5 (release process).** The AGENTS.md release process SHALL include the ship skill's ledger steps (`document-changes --since <prev-tag>`, `baseline create v<ver> --evidence`, `phase-set complete`) so this repository's baselines and phase match its tags.
- **OBL-6 (pins).** Every normative sentence changed under OBL-1 SHALL be pinned in `tests/test_core_skill_text.py` with its SPIKE-008 row id, and pack/checklist text SHALL be covered by `tests/test_prose_cli_surface.py` or a new guard so the same drift cannot return silently.

## Acceptance criteria

- AC1: Given the adoption pack text after this change, when a user runs `specflow baseline create v0.0.0-adoption.1 --evidence` in a fresh project as it prescribes, then the command exits 0 and `adopt status` reports drift after a source change.
- AC2: Given `specflow ci generate` run twice with `PYTHONHASHSEED=1` and `PYTHONHASHSEED=2` on the same config, when the outputs are compared, then they are byte-identical.
- AC3: Given a project in phase `complete` with a baseline for HEAD, when `specflow brief --next` runs, then the first line names `/specflow-discover`.
- AC4: Given a staged `git mv` of an artifact whose status also changes, when the pre-commit hook runs with roles configured, then the RBAC check evaluates the transition.
- AC5: Given the SPIKE-008 Round 1 and Round 2 tables, when each blocking or warning row's source site is re-read, then the quoted claim no longer appears or now matches the engine side.
- AC6: Given `uv run pytest tests/`, when the suite runs after the change, then every new pin passes and `specflow artifact-lint` reports no new findings.
- AC7: Given the AGENTS.md release process after this change, when a release is cut, then `.specflow/baselines/` gains a baseline for the new tag and `state.yaml` reads `complete`.
- AC8: Given a fresh project after `specflow init` and `specflow ci generate`, when the generated workflow is read, then it contains the `specflow-ci-gate` job with its display name `CI gate (RBAC)` and the `specflow-pass-1` job keeps `Pass 1 — programmatic validation`.
- AC9: Given an ops-pack project with one RUN artifact, when `specflow status` runs, then an `Ops:` row appears after the four core rows and projects without extra categories render unchanged.
