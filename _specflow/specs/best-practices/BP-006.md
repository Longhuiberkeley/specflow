# Accounting not policing: surface most signals; reserve blocking for structural integrity and human approval

## Practice
SpecFlow records and surfaces state; the human decides. Signals fall into two tiers:

- **Accounting warnings** (stale docs, suspect artifacts, the `docs-staleness` audit lens) are advisory. They never fail a commit hook and never escalate an audit exit code — they are surfaced for a human to triage, not gated on.
- **Structural signals** (traceability coverage gaps, orphan code, schema violations, consistency breaks) escalate: `specflow project-audit` exits **2** when these are present, and a `release-gate` job may block a release on that exit code. These represent broken integrity, not style — the narrow case worth gating.

Blocking of routine work is reserved for the explicit human approval gate (draft→approved) and for hard structural errors in the commit hook (broken links, invalid schema).

## Rationale
A tool that blocks on every warning trains users to ignore all warnings (cry-wolf) or to bypass the tool. Accounting-with-pointers keeps the human in authority while making problems visible; policing erodes trust and gets disabled. The structural carve-out exists because a silently-broken traceability graph is not a "warning" — it is corrupted accounting that makes every downstream signal untrustworthy, so those few signals earn escalation.

## Verification
The commit hook (`.specflow` pre-commit) exits non-zero ONLY on hard structural errors (broken links, schema violations), never on an accounting warning. `specflow project-audit` returns **0** when only accounting concerns (e.g. docs-staleness) are found, but exits **2** when structural warns (coverage, orphan-code, schema, consistency) are present — and the release-gate blocks on that exit code. No skill coerces a status transition without human confirmation.
