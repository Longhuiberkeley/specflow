# Event-triggered model-checking spikes for stateful mechanisms

## Practice
Run a time-boxed model-checking spike when a trigger below fires, following six steps:
1. Write the invariants first, as a named list (`I<n> Name: statement`) in the DDD. That list is the human-reviewed statement; the model is not.
2. Model the CURRENT protocol and require the checker to reproduce a known defect. This is the fidelity canary; record the tool's specific violation exit code (12 for TLC, checked against the pinned jar), not just "non-zero".
3. Model the fix under the same bounds, with crash and environment actions (git merge, clone, branch kind, hand deletes) as well as process interleavings, and check it.
4. Replay every new trace as a failing pytest on the shipped code before filing a DEF. The DEF's reproduction_steps name that test, `exposed_by` is the test artifact and `derives_from` is the SPIKE. A trace that no pytest reproduces is a modelling error, not a DEF.
5. Fix, then re-check both models; the reproduction test goes from failing to passing and verifies the fix STORY. A DEF left open is pinned as a strict xfail that names it.
6. Record distinct states, exit codes, model and tool sha256, bounds and assumptions in the SPIKE, then dispose of the model.

Put the history variable where the effect becomes durable (a create that reported success, a written journal), not where the code first computes a value; otherwise the checker reports harmless re-plans.

## Applies when
Event triggers only, never the calendar:
- T1: a DEF closes with an ordering, interleaving, retry, resume, lock or crash-recovery root cause.
- T2: a DDD answers the state-machine or concurrent-access question YES for shared state across processes, and the ARCH is safety- or security-tagged or the component already has a T1 DEF.
- T3: code or a doc asserts that a race is impossible or negligible, or that a re-run is safe.
- T4: a REQ acceptance criterion is a pure safety or liveness property of a protocol.

Tool ladder, cheapest first:
- a known window: a barrier pytest (real processes released together at the window);
- several writes a crash can separate: a crash-at-k harness over the write primitives;
- an interleaving of three or more steps across several actors, or git/clone environment actions: TLA+ with TLC;
- algebraic laws of shipped Python (idempotence, round-trips, converse relations): a table test or Hypothesis;
- Lean: never for SpecFlow internals.

## Work products
- A SPIKE with the sections Trigger, Question, Invariants (link to the DDD), Model to code table (model action, code file:line, real-code test), Assumptions (bounds, abstraction, crash and environment model, fairness, tool version and sha256), Fidelity result, Result, Reproductions and Disposition.
- A model under `formal/<tool>/` at the repository root, never under `src/`, whose header reads "valid as of <short sha>; not maintained".
- One DEF per reproduced trace, and a fix STORY verified_by the reproduction test.

## Verification
Inspection, at SPIKE completion:
- Every DEF derived from the SPIKE names, in reproduction_steps, a pytest that failed on the shipped code and, once fixed, passes; an open DEF's test is a strict xfail that names it.
- The SPIKE's Fidelity result records a violation (and its exit code) on the current-protocol model.
- No verify_command, CI job or gate runs the model checker unless the model has been promoted to a maintained artifact; an unpromoted model is never a verify contract.

## Rationale
Model checkers pay off only on interleavings that tests cannot enumerate. Their failure modes are an unfaithful model and a vacuous statement: fidelity-first catches the first, and replaying each trace on real code catches both before a DEF is filed. SPIKE-003 applied the recipe to the index store: the current-protocol model reproduced the known allocation defects, and the model of the fix found two new trace families (DEF-013, DEF-014) that the crash and barrier harness had not, because they need a crash followed by a different command, or a git resolution followed by a create. Keeping the models disposable and outside CI keeps the git-only install free of Java and avoids maintaining a second specification.
