# cascade-status walks only legal transitions, holds REQ verification for unverified siblings, and exits non-zero on any failure (STORY-697 AC1-AC4)

tests/test_cascade_status.py drives specflow cascade-status through cli.main on projects scaffolded from the real .specflow/schema maps (helpers in tests/test_cascade_support.py): a verified STORY with --include-req walks approved REQ/ARCH/DDD through implemented to verified, each write a schema edge; a failing update makes the command exit non-zero and never pairs exit 0 with a failure mark; a REQ with a verified and an implemented implementing STORY is held at implemented (from approved or implemented) and the hold names the sibling; the REQ is verified once every non-terminal implementing STORY is verified; a draft spec is refused with the reason and a non-zero exit; dry-run prints the legal walk and writes nothing; derives_from REQ links cascade like implements; specs already at or beyond the target are left alone. tests/test_cascade_legality_table.py is the exhaustive table: for every story status x include-req x sibling state, the STORY links a REQ, ARCH and DDD in every status its real schema allows, and every recorded (type, from, to) status write must be an allowed_status edge; the pure legal_walk planner is checked over every (from, goal) pair; the status-cascade lint and cascade-status share one CASCADE_ROLES object whose roles are legal story link roles. On the shipped code 8 cascade cases and 9 table cases failed (approved -> verified proposed in one hop, a self-loop implemented -> implemented, exit 0 with a failure mark, REQ verified with an unverified sibling).
