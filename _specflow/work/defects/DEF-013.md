# Allocators ignore a crashed renumber journal and rewritten frontmatter ids: a create before the re-run takes a journalled id, duplicates it, and the resume stops on a collision

Found by TLC on the fixed-protocol model formal/tla/IdAllocation.tla (SPIKE-003 part 2) and replayed on the real code by UT-132 (tests/formal/test_index_store_model_traces.py, strict xfail). The protocol assumes a crashed renumber is re-run before any other writer; the mutation lock is released when the process dies, so any create, update or rebuild can run in between. The model variant IdAllocation_CandidateFix.cfg (every allocator also floors on the journal targets and on every frontmatter id, not only file stems) checks clean: 4,359,816 distinct states, depth 36, exit 0. Not fixed in this package; a fix STORY should be verified_by UT-132 with the xfail marks removed.
