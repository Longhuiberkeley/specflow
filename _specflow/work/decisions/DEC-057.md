# D-19/D-20: Adoption Pack — brownfield adoption via ARCH-per-component code-linking

## Context

SpecFlow's narrative and tooling were greenfield-only: `init → discover → plan → execute → ship`. A team with an existing codebase had no guided way in. The primitives existed (create accepts any status, baseline snapshots whatever exists, detect orphan-code --retro-link), but no skill orchestrated them for adoption.

## Decision

### D-19: Adoption as an opt-in pack

Adoption is delivered as an opt-in `adoption` pack (not a core skill), because greenfield users never need it. The pack adds one skill (`/specflow-adopt`) that drives existing CLI. The one new concept is the as-built baseline: inventory → backfill core artifacts (tagged `backfilled`) → cut `baseline adoption-v0`. Provenance uses existing fields only (`tags: [backfilled]` + `rationale`). No new status, no new artifact type, no schema change.

### D-20: ARCH-per-component code-linking, zero STORYs, globs as core

Three coordinated changes:

1. **Code-linking homes are ARCH and DDD, not STORY.** Adoption creates zero STORYs. ARCH `output_files` is the custody record (typically a package glob). STORY is reserved for forward action.

2. **`output_files` globs are a core feature.** `lib.files.expand_output_files` is the single source of truth. All consumers (orphan meter, reconcile, source-drift) route through it.

3. **Completeness is derived from the graph.** `specflow adopt status` projects coverage %, per-ARCH boundary dashboard, per-artifact completeness on demand. No state file.

The default large-repo strategy is skeleton-first: one ARCH per component (15-30 artifacts), then deepen with `adopt status` as the steering signal.

## Rationale

Semantically, code realizes an architecture — a backfilled STORY for shipped code is a category error. Globs are the only way to make huge-codebase adoption tractable. Deriving completeness from the graph respects "the repository IS the database." Skeleton-first makes the sequential core work at any scale.
