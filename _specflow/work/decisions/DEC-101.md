# Staged DDD-shape accounting: a REQ whose V-model thread has an implementing STORY owes no DDD refinement (amends DEC-099)

# Staged DDD-shape accounting (amends DEC-099)

## Context

The tag-run Release gate (project-audit, no continue-on-error) has been red — exit 2 — since v1.16.0. The escalating set was 12 rows: 11 vertical "ARCH exists but no DDD refinement" rows plus the 1 orphan-code row. Two corrections to the prior summary of this debt:

- The 4 STORY-642..645 "no test verification" rows were ALREADY accounting (concern=verification, registered pre-v1.17.x) and never escalated — the stale prior summary counted them as gate pressure.
- The dry-run renderer suppresses the concern tag on the vertical axis (project_audit._print_dry_run_findings: no (group) suffix for axis=vertical), which is exactly why accounting vertical rows LOOK structural in CI output.

Of the 11 DDD rows, 2 were walk false-negatives, not policy: DDD-033 carries specified_by ARCH-039 (a legal detailed-design shape, role_targets.py), but the old thread walk credited only a DDD whose OWN links carried refined_by/derives_from at a thread member. It missed both that DDD-held specified_by shape and the canonical PARENT-HELD shape (an ARCH own links[] carrying refined_by -> DDD) that check_coverage already credits (artifact_lint.py, STORY-679). The truthful-walk fix removes the REQ-052/REQ-053 rows entirely.

The remaining 9 REQs (REQ-039/040/042/045/046/047/055/056/057) genuinely have no DDD — and all 9 have implementing STORYs: the work is realised.

## Decision

Predicate: **a REQ whose V-model thread has an implementing STORY owes no DDD refinement.** Concretely, when the vertical walk finds has_arch TRUE, has_ddd FALSE and has_stories TRUE (a STORY implements ANY thread member), the "ARCH exists but no DDD refinement" row is still emitted — truthful, printed, stamped, CHL-minting — but carries concern=ddd-shape, registered in _ACCOUNTING_CONCERNS, so it can never drive exit 2. When has_stories is FALSE the row keeps NO concern and escalates exactly as before.

Gate-equivalence note (do not erode): the concern-less no-ARCH and no-STORY rows are untouched and still escalate; their shared rule id audit/lens:general is NEVER registered accounting. Nobody may later "simplify" by stamping ddd-shape (or any concern) unconditionally — that would blind the gate to genuine V-model holes. Concern classification is part of the cached findings (gen-3 doctrine), so _CACHE_GENERATION bumps 6 -> 7.

## Rejected alternatives

1. **Author 11 retroactive DDDs** to silence the rows. This is the C-7 anti-pattern named in DEC-095 — "link reshaping chosen to silence lint rather than to describe the design" — and the artifacts would be precisely the "DDD content that duplicates the ARCH" that ddd-selection.md:59 forbids.
2. **Blanket lens:general accounting registration.** lens:general is the shared rule id of the escalating no-ARCH/no-STORY rows; registering it would blind the gate to real V-model holes.
3. **Wire the audit exit to the findings-baseline.** That is P4 scope, and project-audit never loads the baseline today — its exit is count-based (errors -> 3, escalating warns -> 2). Pretending otherwise hides the change inside a mechanism that does not exist yet.

## Normative division of labour

The ddd-selection.md 6-question tree stays the PLANNING-TIME authority for whether a component owes a DDD. The audit row is a heuristic proxy: it cannot distinguish "the tree said NO" from "we forgot" — which is why it is accounting (review prose, still printed and stamped) and never a gate.

## Residual risks

- **One-way silence.** After this decision NO engine surface escalates on DDD absence *while the thread has an implementing STORY* — with no implementing STORY the no-DDD row still escalates (pinned by tests/test_project_audit_ddd_shape.py); findings baselines only shrink (resolved keys drop out). A strict-standard consumer that genuinely requires DDD coverage has exactly one path: pack clause coverage via complies_with links (standards-coverage lens). Recorded, accepted.
- **has_stories ignores STORY status** — one draft STORY suffices to stamp the row accounting. Chosen, not accidental: planning-order noise (STORY minted before implementation) must not flip a release gate, and the row still prints for review.

## Consumer parity

Generated release gates (lib/adapters/github_actions.py) run project-audit WITHOUT continue-on-error, so consumer gates flip red -> green on upgrade for exactly these rows — the same parity note DEC-095 recorded for the lint baseline.

## Docs note

docs/architecture.md and docs/lifecycle.md render REQ -> ARCH -> DDD -> STORY as the full-V template, not an obligation; the modeless/scale-adaptive doctrine (AGENTS.md section 2) already licenses lean paths, and this decision aligns the audit DDD rung with it. No doc change required.

## Risk tier
