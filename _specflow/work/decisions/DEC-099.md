# Findings-baseline ratchet replaces run-count escalation; escalating vs accounting classes

## Decision
artifact-lint findings become typed records `Finding(rule_id, subjects, severity, class, args)` (ARCH-039 migration order, P3). The exit code is a pure function of the repository, an explicit `--as-of` date and the committed `.specflow/findings-baseline.yaml`:

- A blocking finding fails the run.
- On a full run (no `--type`), an escalating warning whose key `(rule_id, subjects)` is not in the baseline fails the run. Keys in the baseline are known debt and do not fail it. Baseline keys no longer produced are reported as resolved.
- Accounting findings and info never fail a run. `--type` runs never escalate, so the pre-commit hook is unchanged.
- rule_id is per finding kind (`links/orphan`, `links/missing-v-pair`), and subjects carry a discriminator (target id, path). Two different problems on one artifact are two keys. Counts, ages, hashes and samples live in args and never change a key.
- The baseline file lists sorted `(rule, subjects)` entries, with no counts or timestamps, and is byte-idempotent, so it merges cleanly across worktrees.
- Its only writer is `specflow findings-baseline update`. `init` calls that routine to write an empty baseline.
- `update` seeds when the file is absent and always drops resolved keys. Keys not yet in the baseline are added only with `--accept-new`, which prints every added key and is approval-gated under the always-on rule. Without `--accept-new`, `update` writes nothing when new keys exist, lists them, and exits 1.
- Absent baseline: the ratchet is off, and every full run prints a hint. Sunset: from v1.18.0 an absent baseline reads as empty.
- Accounting rules are fingerprint-drift, bp-application, dead-oracle (the former exemptions) and the ARCH-039 heuristics: conflicts, quality, ac-observable, dec-risk-profile and spike-lifecycle staleness. Spike zombie and repeated-topic findings stay escalating.
- artifact-lint writes nothing under `.specflow/` (REQ-053 AC2). The source-drift store is seeded by `init`/`refresh` when absent and by `specflow fingerprint-refresh --source`, never by lint. `--fix` is an explicit mutation mode and is outside AC2.
- Environment inputs are explicit (AC9): `--as-of` (default today, UTC) drives spike staleness, and an `Inputs:` line records the as-of date and the source-drift store state.

## Rationale
STORY-663 escalated a warning after three consecutive full runs and kept per-line counters in the tracked `.specflow/lint-warning-history.yaml`. Every lint, artifact-review and CI run advanced them. In consumer repos where agents lint often, 700 warnings became "blocking" with no change in findings (cs2_bet, 2026-09-30). Identical repositories gave different exit codes depending on how often someone had looked. The counters also keyed on rendered text, so a count inside a line reset its identity. SPIKE-002 allowed deleting the escalation claim, and REQ-053 AC7 names the replacement: a committed baseline that can only shrink without an explicit, reviewed acceptance. Making heuristics accounting follows ARCH-039: a text-quality regex must not decide an exit code.

## Consequences
- Consumers keep passing on upgrade (ratchet off until they run `findings-baseline update` once and commit). The v1.18.0 sunset turns that into strict-by-default. Refresh deletes the obsolete history file.
- renumber-drafts changes draft ids in keys. Run `findings-baseline update --accept-new` in the same change.
- Deleting the baseline turns the ratchet off until the sunset.
- Patch-release semantics change is recorded prominently in the v1.17.1 CHANGELOG upgrade note.
