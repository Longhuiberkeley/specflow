# Engine direction: Python shell plus one declarative ontology and named graph views; formal methods as user evidence and targeted spikes; no specflow2

## Decision
SpecFlow's engine stays Python. Its semantics move to ONE declaration: `src/specflow/core/ontology.yaml` (types, kinds, lifecycles, link roles with a single orientation each, role-target matrix, normative fields), compiled into a frozen registry, with one canonical graph per invocation and NAMED views (coverage, chain depth, suspect, approval staleness, verified-contradiction) that every command calls. Findings become typed records keyed by (rule_id, subject); the exit code becomes a pure function of the repository plus a committed findings baseline. Artifact types are classified into four KINDS declared as data, with no file moves or prefix renames: CLAIM (REQ, ARCH, DDD, BP, ADR-style DEC, test specs), WORK (STORY, SPIKE, pack COMP/LOOP), EVIDENCE (change-record DEC, AUD, baselines, verify runs, pack EXPT/RUN/MON), JUDGMENT (CHL, REVIEW, DEF, approvals, tailoring). Evidence stays in the trace graph but leaves coverage denominators, suspect cascades and orphan counts.

Formal methods are adopted in two places only: (a) as USER evidence, a UT/IT/QT whose verify_command runs a model checker or proof assistant, with deterministic hygiene lint rules; (b) as time-boxed, repo-only model-checking spikes on SpecFlow's genuinely stateful mechanisms (next_id allocation under parallel waves; renumber-drafts crossing rebuild-index), recorded as SPIKEs whose counterexamples become DEFs. A Lean-hosted engine, a Datalog engine built up front, a specflow2 rewrite, a fork, and a long-lived dual v1/v2 reader are rejected. The Datalog rule layer is gated on the standards pilot (REQ-055) showing that packs need user-authored quantified rules.

Cutover is a strangler fig inside 1.x in the same repository and package. All on-disk changes are additive (config `format_version`, optional `links[].fp`, optional `approved_by/approved_at/approved_fp` using a versioned `fp2:` scheme, optional clause fields, pack `profile.yaml`, `.specflow/findings-baseline.yaml`). The v1 body fingerprint, baselines, the ID scheme, the 30 `artifact-lint --type` names and exit codes, the CLI verbs used by skills, and the AGENTS.md sentinels are preserved. A 2.0.0 is bumped only if stored approved/verified status becomes derived from evidence, and ships with one idempotent `specflow migrate` generalised from `practices migrate`.

## Rationale
Two adversarial ultracode studies on 2026-09-30 (six readers, three opposed proposals, three skeptical judges, a synthesis and a completeness critic) converged unanimously on this path. The owner's pain (weaker agents let drift in) is a single-source-of-truth failure: about ten duplicated type registries, eight independent implementations of "is it traced", three edge-direction implementations, findings stored as rendered strings and re-parsed for identity, a dormant suspect cascade (`impact_analysis.auto_flag` never read; `propagate_suspects` has one caller with `force_minor=True`), and a confirmed latent coverage divergence (`check_coverage` ignores the canonical `REQ refined_by ARCH` shape that `role_targets.py` declares). A prover does not fix this: when the rules are the spec there is no independent theorem; the meta-properties (lifecycle reachability, one orientation per role, matrix closure) are finite and decidable by a short pytest; auditors give no tool-confidence credit for a proven link checker (ISO 26262-8 cl.11 TD comes from downstream detection); and a Lean toolchain would break the git-only, pyyaml-only install. The premise about Anthropic's Lean use was corrected: the target was the Claude Agent SDK, the method was model-then-counterexample bug hunting in Lean and TLA+, not whole-codebase proof.

Backward compatibility is a non-issue for users (the owner's own repos; generated CI pins `@v<ver>`) and a real constraint only for data and interface surfaces, including the unpinned bare-`specflow` pre-commit hook. The 1,634 tests and the 877-artifact dogfood corpus are the parity oracle that makes an in-place engine change safe; a rewrite would discard them.

## Consequences
- Every new registry or constant for types, roles or lifecycles goes in `core/ontology.yaml`; an architecture test bans type and role string literals outside `core/`.
- Coverage and V-pair metrics may shift when definitions are unified; each shift is recorded in a DEC citing REQ-012/REQ-013.
- New derived states (suspect, approval_stale, verified_contradiction) start at accounting severity; no status is auto-revoked in 1.x.
- Consumer hooks run whatever engine is on PATH, so the hook gains a `format_version` guard.
- The README must not imply standards compliance until the REQ-055 pilot has published its numbers.
- Superseded prior direction: none. This decision guides REQ-052..058, ARCH-039, ARCH-040, DDD-033, DDD-034, SPIKE-003, SPIKE-004 and the metric-delta records DEC-091..093.
