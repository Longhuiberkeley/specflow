# Staged findings classes: test-linkage rows are accounting until implemented; authoring-shape advice is accounting (amends DEC-099)

## Decision

Amends the class table of DEC-099 (`src/specflow/core/policy.py`). Keys `(rule_id, subjects)` are unchanged everywhere; only the class moves.

- **Staged rules** — `coverage/no-test`, `links/missing-v-pair`, `bp-application/no-test`: *accounting* while the subject STORY/spec is `draft` or `approved`; *escalating* once the subject is `implemented` or `verified`. The check passes the subject's status to `klass_for`; a staged rule emitted without a status is accounting (nothing has been claimed).
- **Authoring-shape advice** — `wave-cycles/fan-in` and every `story-size/*` rule: always *accounting*. `wave-cycles/cycle` stays escalating.
- **Lean path** — `coverage/no-arch` on an approved REQ is *accounting* when at least one STORY links to it via `implements`/`derives_from` (any status): the planner chose to realise the REQ without an ARCH, which is a legitimate scale-adaptive shape. With no STORY at all it stays escalating (and `coverage/no-story` fires beside it). This repository's REQ-059, REQ-060 and REQ-061 are the lean case.
- **V-pair scope** — `find_missing_v_pairs` examines `approved`/`implemented`/`verified` specs only. A `draft` spec owes no pair yet; a `cancelled`/`deprecated`/`superseded` spec owes none any more. `specflow status` missing-pair counts follow.
- `bp-application/no-test` was already accounting through the `bp-application` prefix; it is listed as staged so that a future status-aware emit escalates at `implemented` without another amendment.
- **project-audit parity** — lean-path `coverage/no-arch` rows are routed to the accounting `coverage-shape` concern in both the cross-cutting coverage roll-up and the vertical thread row (`check_coverage` reports them as `lean_path_warning_count`, outside the structural count); an approved REQ with no STORY stays under `completeness` and escalates.
- Unchanged: `coverage/no-story` escalates from REQ approval; `--type` runs never escalate; the baseline file format and its single writer.

## Rationale

`init` writes an empty baseline, so every escalating warning on day 0 is new. Before this amendment a fresh project at discovering/planning/executing with approved STORYs and no tests failed with `FAIL (N blocking [N new vs findings baseline])` — 490 in one consumer transcript, 78 in this repository after 13 approved STORYs were minted. Agents answered with `--accept-new` three times (baseline 62 → 614) and with link reshaping chosen to silence lint rather than to describe the design (C-7). Debt is a claim of done-ness that the artifacts do not back; before `implemented` nothing has been claimed, so the row is a standing fact. Accounting-not-policing: every row still counts in the warning total; the condensed default view lists only new lines and `--verbose` prints every row — only the exit code changes. Measured on this repository: 78 new escalating rows before the amendment, 42 after (excluding source-drift noise from concurrent edits) — the 42 are 39 `coverage/no-test` rows on 7 STORYs moved to `implemented` without UT/IT/QT (the intended escalation) and 3 `thinking-techniques/unchallenged` rows on approved REQ-059..061. This amendment does not make day 0 clean in every phase; see the open question below.

## Consequences

- Baseline entries for staged rows whose subject is still approved are reported as resolved and drop on the next `specflow findings-baseline update` (7 in this repository). When that subject later moves to `implemented`, the row escalates again and must be fixed or accepted with `--accept-new`.
- `artifact-lint` default view prints, per check, `N known (baselined), M new[, K accounting]` and lists only the new lines; `--verbose` (or a single `--type` run) prints every line. Exit codes never depend on the view.
- Rejected: escalate only after N runs (resurrects the STORY-663 counter DEC-099 retired); collapsing per-type `coverage/no-test` rows into one (churns baseline keys); making `coverage/no-story` accounting before planning (residual: an approved REQ with no STORY yet still escalates — plan it or baseline it).
- **Pre-planning staging (decided 2026-10-08, closes the discovering-phase residual).** While the project has not entered the planning phase (`state.yaml` `current` is `idle` or `discovering`), the planning-gap rows on a REQ subject — `coverage/no-story`, `coverage/no-arch` and `links/orphan` — are *accounting*: between `/specflow-discover` and `/specflow-plan` an approved REQ with nothing downstream is the expected state, not debt. From `planning` on they escalate exactly as before; the staged test-linkage rules ignore the phase. `klass_for(..., pre_planning=True)` is passed only for REQ subjects (`PRE_PLANNING_RULES` / `PRE_PLANNING_PHASES` in `core/policy.py`). Options rejected: seeding the baseline from `init`/`discover` (hides the rows instead of classing them) and leaving the day-0 FAIL (cry-wolf by the project's own definition).
