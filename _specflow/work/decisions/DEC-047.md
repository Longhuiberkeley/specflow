# EXPT artifacts are write-once with terminal status

## Context

All other SpecFlow artifact types have status workflows (e.g., requirement: draft → approved → implemented → verified). For EXPT we considered the same pattern.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| **Workflow status** (running → kept/discarded) | Consistent with other types | Loops produce 100s of EXPTs; transitions add overhead and create stale 'running' rows on crashes |
| **Terminal status** (chosen) | EXPT is created in its final state; no follow-up writes; immutable audit trail | Different from other types — requires schema-validator to permit creation directly into any allowed_status |

## Resolution

EXPT schema declares four terminal statuses with empty prior-state lists:

```yaml
allowed_status:
  kept: []
  discarded: []
  crashed: []
  no_op: []
```

The existing `create_artifact` in `artifacts.py` already accepts creation into any allowed_status key (REQ enters as `draft` the same way). A test must confirm the four EXPT statuses all permit direct creation.

## EXPT id_format

Standard SpecFlow ID format is `\d{3}` (max 999). The plan's target of "100-1000+ experiments per competition" exceeds that. EXPT widens to `\d{4,5}$` (max 99999). IDs remain globally sequential, not per-COMP.
