# COMP is the top-level scope, not project or strategy

## Context

Several scopes were candidates for the top-level abstraction.

## Options considered

| Scope | Why rejected |
|---|---|
| **Project** (= the whole repo) | Too coarse — one repo can host multiple unrelated problems (screener competition + validator competition). FINDs from one problem would pollute the other. |
| **Strategy** (= a code-level approach) | Too fine — strategies change rapidly across EXPTs. Strategies are a *result* of research, not the *scope* of it. |
| **Competition** (chosen) | Right granularity. A COMP defines dataset + metric + verify_command — the contract a LOOP optimizes against. |

## Resolution

COMP is the top-level scope. Two consequences:

1. **FINDs live at COMP level.** A new LOOP reads all confirmed FINDs for its COMP before starting. This is the knowledge condensation mechanism.
2. **Cross-competition is a special case, not the default.** When the same repo has multiple COMPs (e.g., screener + validator), the user manually creates a validate-mode LOOP on COMP-002 that reads FINDs from COMP-001. No automation in v1.

## Trust boundary

`verify_command` on COMP is executed by the agent. Only the project owner should edit COMP artifacts. Document this in `competition-setup-protocol.md`.
